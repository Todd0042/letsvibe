How LetsVibe grades a project

LetsVibe ranks vibe-coded projects: programs written by AI from someone's prompts, usually by people who are not programmers. Every grade is produced by programs and open AI models running on LetsVibe's own computer. Your code is never sent to an AI company. This page explains every step, including what the grades do not mean.

In short: a program builds an app dossier and runs a static code scan (screens, setup, launch, saving, and proven problems), a unified 30.5B Mixture-of-Experts model (Qwen3 30B-A3B running locally via CUDA llama.cpp --cpu-moe) synthesizes the project's purpose, audits the source code in large 12K-token batches with exact file and line citations, and produces calibrated 5-factor scores, actionable developer next steps, and a plain-English verdict.

Archetype-aware grading: Projects are judged through the lens of what they actually are (Developer Tools/MCP Servers, Games, Media Lounges, Mobile/IoT, Automation Pipelines, or General Software) rather than holding everything to generic consumer web SaaS expectations. Developer utilities are rewarded for CLI clarity and schema precision without being dinged for lacking web screen-reader tags; games are judged on gameplay feel and arcade feedback rather than business forms.

Direct rubric scoring + community Spark upvotes. Every project receives a direct 0–100 rubric score for that commit, plus a bounded diminishing-returns bonus from community Sparkle (✨) upvotes (capped at +3.0 points, clamped at 100.0).

Vibe-coded software is graded as vibe-coded software. Every project is compared with other vibe-coded projects, never with software written by professional developers. "Good enough" is the standard: a project is graded on what it gives the people who use it, not on how its code is written or how long it took to make.

Step by step

  1. You submit your own GitHub repository. You sign in with GitHub so we can confirm the repository belongs to your account; you cannot submit someone else's work. You can target a specific branch or subfolder URL (for example /tree/main/v4.0), and if a repository is a multi-version archive root, LetsVibe prompts you to submit the specific version folder. For plugins, mods, or addons that depend on an external engine or host framework not committed in the repo, you can click [+] to attach up to 5 read-only reference contexts (public https:// repo/header URLs or local .h/header uploads); only the main repository is graded and counted in LOC. If the latest commit has already been graded, nothing runs again.
  2. Vibe-coded check. LetsVibe is for projects written by AI from someone's prompts. Projects whose history starts before November 2022 (before vibe coding existed) and forks of someone else's project are not graded. Strong signs of vibe coding are AI tool files (such as CLAUDE.md, AGENTS.md, GEMINI.md or Cursor and Copilot instructions), AI co-author lines in a real share of the commits, AI app-builder accounts as commit authors, a README that says so, or code with several habits typical of AI-written code. Weaker signs, such as install scripts or README badges, never decide on their own, and code examples in documentation are never counted. If the check cannot confirm a project was vibe-coded (copying code from a chat window, for example, leaves few traces), the project is still graded, and the site owner reviews it before it is published.
  3. A temporary copy is made. The repository is cloned into a temporary folder on LetsVibe's server. Bundled third-party libraries and generated files are set aside so the project is judged on its own work, while any host/SDK headers (such as Nexus.h) #included by your source files are deterministically scanned in Python for their capability surface and API symbols (without adding them to LOC or Code Health) so plugins aren't penalized for host-managed windows, options, or lifecycle. The copy is deleted when the evaluation ends.
  4. Archetype & Classification. Build files (for example platformio.ini, an Android manifest, MCP tool descriptors, or canvas/game engines) and documentation identify the project's archetype: Developer Tool / MCP Server, Game / Interactive Simulation, Media / Audio Lounge, Mobile / IoT, Automation Pipeline, Web Productivity, or General Software. This archetype determines the specific evaluation lenses and domain exemptions applied throughout the grade so software is judged fairly for its intended purpose.
  5. The App Dossier (no AI). A program reads the repository and writes down what a person experiences: what the project says it is (its README, bypassing top-of-page badge walls, donation buttons and hero images to find the true pitch, and counting visual screenshots and diagrams as proof of work), the libraries and data it uses, its screens, whether several devices can use it at once (for example a TV, a host screen and guests' phones kept in sync), the program's own features, the text people read on screen, how it is installed and launched, how much must be filled in or understood before first use, whether it saves your progress or data, and any ads, payments or required sign-in found in its code (never words in its story or on-screen text). Nothing in the project is ever run.
  6. Context & dossier synthesis (30B-A3B). Qwen3 30B-A3B reads the project's README, commit/release context, and app dossier in a 32K-token context window to identify the true archetype, target audience, and initial observations across all five factors.
  7. Deep code audit in 12K-token batches. The repository's own source files (excluding untouched vendor/SDK code) are packed into large 12,000-token batches with line numbers preserved. The model audits each batch directly for verified strengths, bugs, stubs, missing error handling, and creative mechanics, citing exact files and line numbers.
  8. Calibrated scoring & next steps. Combining deterministic telemetry, static scan findings, the dossier, and every batch audit, the model scores the six weighted factors (Real-world Value 25%, Functionality 20%, User Journey 15%, Code Health 15%, Creativity 15%, UI/UX 10%) and generates concrete, prioritized developer next steps.
  9. Written review & verdict. A final pass turns the verified findings and scores into a plain-English verdict title, executive summary, peer takeaway, and per-factor explanations grounded in the cited code.

If any stage fails or returns incomplete results, or a grade runs longer than 60 minutes, no grade is published at all. We would rather show nothing than a misleading number.

The five factors

In order of weight: real-world value, creativity, user journey, functionality and UI/UX.

FactorWhat it measures
Real-world valueIs it more than what a single short prompt would make? Does it adapt a common idea for a real niche, solve a problem that free tools overcomplicate, or keep people coming back? Features beyond the basic idea count, when the dossier shows them.
CreativityJudged on the human-facing design, never on the code: on-screen text with personality, an unusual way of using it, how richly themed it is, and whether its features combine into one experience.
User journeyFrom installing it to closing it: how it launches, whether you land on the main thing or are buried in menus, how much must be filled in before first use, whether your progress or data is kept, and any ads, payments or required sign-in found in its code (never words in its story or on-screen text).
FunctionalityDoes what is built actually work for the person using it? Can the main task be done from start to finish, are the features wired together, and does the app tell people when something worked or went wrong? Problems a program can prove count against it, such as back-end features no screen ever calls or a config file that cannot be read, measured per 1,000 lines of code so a bigger project is never punished for its size.
UI/UXThe screens or user interfaces themselves (web, mobile, desktop, or terminal/CLI), judged for the device and archetype it is made for: clear layout, consistency, feedback while people wait, and ergonomics. Technical terminology is welcomed as an asset for developer tools and APIs.

When neither the dossier nor the code shows evidence either way (a scan that found nothing proves nothing), the answer is "not shown" and earns middle points: something a program cannot prove is never held against a project. Code complexity is described on every report in plain English (how many paths the average function has, the most complex functions, very large files and repeated code), for information only: it never counts toward the score. Other code-health notes (unused files, ignored errors) are shared with each project's owner only. Safety is not graded: LetsVibe is not a security tool. Size never counts on its own: lines of code and number of files are not quality signals.

What the grades mean

A factor's score is the share of its checklist points the project earned, and the overall score weights the five factors (above). Community Sparkle (✨) upvotes add up to +3.0 points directly on top of the rubric score (clamped at 100.0). Every report also shows its rank in its category (for example "#3 of 41 in Games"). Community Sparks (upvotes)

Signed-in visitors can click the Spark (✨) button on any public project card or report page (unlimited across other people's projects, and at most one of your own repositories). Sparks add a bounded diminishing-returns bonus of min(3.0, 0.5 × log2(1 + sparks)) (+0.50 for the first Spark, +1.00 at 3 Sparks, capped at +3.00 total) directly to the project's score (clamped at 100.0), and deleting your account removes all Sparks you cast.

What a LetsVibe grade is not

  • Not a security audit. A published report never certifies that software is safe to run.
  • Not an endorsement of a project, its author or its fitness for any purpose.
  • Not perfectly repeatable. AI models vary slightly from run to run, so the same code can score a few points differently. Treat small differences between projects as a tie.
  • Not a judgement of a person. Grades describe a repository at one commit, under one rubric version.

Corrections

AI reviews can get facts wrong. A project's owner can report an error in any statement of their review, pointing to the relevant code. The statement is checked once against the code; if the check confirms the error, the statement is corrected (in live data and backups) and the report shows that it was corrected. Otherwise it is reviewed by hand. Scores are not changed by a correction; the owner can request a fresh grade after pushing a new commit.

Why everything runs locally

Engine v10 runs locally on LetsVibe's own machine using CUDA-accelerated llama.cpp (--cpu-moe) with Qwen3 30B-A3B: attention layers and the 32K context cache stay in GPU VRAM on an RTX 5060 Ti while Mixture-of-Experts weights run from system RAM on CPU. Nothing you submit is sent to OpenAI, Anthropic, Google or any other AI provider, and nothing is used to train models. An evaluation typically takes 2–6 minutes and runs one at a time.
