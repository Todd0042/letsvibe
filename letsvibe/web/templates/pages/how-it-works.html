How LetsVibe grades a project

LetsVibe ranks vibe-coded projects: programs written by AI from someone's prompts, usually by people who are not programmers. Every grade is produced by programs and open AI models running on LetsVibe's own computer. Your code is never sent to an AI company. This page explains every step, including what the grades do not mean.

In short: a program writes down what people experience in the project (its screens, the text on them, how it is set up, launched and saved), the project is compared with common app types people make from a single prompt, a model answers fixed checklists about it one topic at a time and quotes its evidence for every answer, a second model separately reads the code one topic at a time and must quote the lines it relies on, the two are compared item by item, and each answer is worth fixed points. No AI picks a number.

LetsVibe grades on a curve (a bell curve). Your letter grade comes from where your project sits between two published reference projects and, as your category grows, how it compares with the projects in it. Everything behind the curve, every number included.

Vibe-coded software is graded as vibe-coded software. Every project is compared with other vibe-coded projects, never with software written by professional developers. "Good enough" is the standard: a project is graded on what it gives the people who use it, not on how its code is written or how long it took to make.

Step by step

  1. You submit your own GitHub repository. You sign in with GitHub so we can confirm the repository belongs to your account; you cannot submit someone else's work. If the latest commit has already been graded, nothing runs again.
  2. Vibe-coded check. LetsVibe is for projects written by AI. We look for signs such as AI-assistant configuration files (Cursor, Copilot, Windsurf, Cline, Aider and similar) and AI co-author lines or prompts in the commit history. If none are found the project is not graded, and you can appeal.
  3. A temporary copy is made. The repository is cloned into a temporary folder on LetsVibe's server. Bundled third-party libraries and generated files are set aside so the project is judged on its own work. The copy is deleted when the evaluation ends.
  4. Classification. Build files (for example platformio.ini, an Android manifest or an Xcode project) tell us which platforms and hardware the project targets. A small model then reads the README and the file layout to pick a category, used for the category rankings and filters.
  5. The App Dossier (no AI). A program reads the repository and writes down what a person experiences: what the project says it is (its README and window titles, quoted as the owner's own words), the libraries and data it uses, its screens, whether several devices can use it at once (for example a TV, a host screen and guests' phones kept in sync), the program's own features, the text people read on screen, how it is installed and launched, how much must be filled in or understood before first use, whether it saves your progress or data, and any ads, payments or required sign-in found in its code (never words in its story or on-screen text). Nothing in the project is ever run.
  6. Common app types (no AI judgement). A small local embedding model compares the project with a list of app types people commonly make from a single prompt (to-do lists, stock viewers, space shooters and so on). The closest one, and how similar it is, is given to the reviewer as a plain fact.
  7. The code, one topic at a time. The project's own code is cut into small sections. A 7B model (Qwen2.5-Coder 7B) reads each section separately for one topic at a time (functionality, UI/UX, user journey, creativity), and only the sections that can tell it something about that topic: screens for UI/UX, setup and launch code for the user journey, and so on. It answers the same fixed-choice checklist as below and must copy the exact lines of code behind each answer. A program checks every quote against the real file; answers whose quotes are not in the code are thrown away.
  8. Checklists on the dossier, one topic at a time. A 14B model (Qwen2.5-Coder 14B) reads the dossier and answers five separate checklists: real-world value, creativity, user journey, functionality and UI/UX. Every answer is a fixed choice (for example "a common idea adapted for a niche" or "setup is heavy before first use"), and every answer must quote the dossier as its evidence; a program checks that each quote is really there.
  9. The two reviews are compared. Item by item: when they agree, the answer stands; when only one found checked evidence, that evidence is used; when they disagree, the 14B rereads the exact quoted lines from both sides and says which claim the code supports, quoting the line that decides it. If neither claim holds up, the item counts as "not shown". Answers are never averaged, and every decision is kept with the report.
  10. Points (no AI). Each answer is worth fixed points, published below. The model never picks a number, so every score can be traced to the answers behind it.
  11. The written review. The 14B rewrites the checked answers in plain English, pointing to the file and line where a finding was seen. "Needs work" lists only genuine problems found by the checklists (such as a heavy setup, nothing being saved, or a standard copy of a common idea); if there are none, it says so instead of inventing advice.

If any stage fails or returns incomplete results, or a grade runs longer than 3 hours, no grade is published at all. We would rather show nothing than a misleading number.

The five factors

In order of weight: real-world value, creativity, user journey, functionality and UI/UX.

FactorWhat it measures
Real-world valueIs it more than what a single short prompt would make? Does it adapt a common idea for a real niche, solve a problem that free tools overcomplicate, or keep people coming back? Features beyond the basic idea count, when the dossier shows them.
CreativityJudged on the human-facing design, never on the code: on-screen text with personality, an unusual way of using it, how richly themed it is, and whether its features combine into one experience.
User journeyFrom installing it to closing it: how it launches, whether you land on the main thing or are buried in menus, how much must be filled in before first use, whether your progress or data is kept, and any ads, payments or required sign-in found in its code (never words in its story or on-screen text).
FunctionalityDoes what is built actually work for the person using it? Can the main task be done from start to finish, are the features wired together, and does the app tell people when something worked or went wrong? Problems a program can prove count against it, such as back-end features no screen ever calls or a config file that cannot be read, measured per 1,000 lines of code so a bigger project is never punished for its size.
UI/UXThe screens themselves, for the device the app is made for: clear or cluttered, one consistent look or a patchwork, feedback while people wait, and whether it suits its phone, TV, desktop or terminal.

When neither the dossier nor the code shows evidence either way (a scan that found nothing proves nothing), the answer is "not shown" and earns middle points: something a program cannot prove is never held against a project. Code complexity is described on every report in plain English (how many paths the average function has, the most complex functions, very large files and repeated code), for information only: it never counts toward the score. Other code-health notes (unused files, ignored errors) are shared with each project's owner only. Safety is not graded: LetsVibe is not a security tool. Size never counts on its own: lines of code and number of files are not quality signals.

What the grades mean

A factor's score is the share of its checklist points the project earned, and the overall score weights the five factors (above).

Letter grades are given on a curve, often called a bell curve. A raw score says little on its own, so it is not turned into a letter directly. Your letter depends on how far your score sits above or below the average, measured in standard deviations; on a full bell that gives about 7% A, 24% B, 38% C, 24% D and 7% F.

  • Two public reference projects set the ends of the curve. A small app written to satisfy every factor and one written to ignore every factor were each graded several times with exactly the pipeline your project goes through. Until your category has projects of its own, the bell's average is the midpoint between them and one standard deviation is a quarter of the gap, so the good one sits two standard deviations above average and the bad one two below.
  • Your category takes over as it grows. Each project added to your category shifts the bell toward that category's own average and spread, and from 30 projects on, the bell comes entirely from your category.
  • Two rules keep it honest: an A also needs a score near the top reference, so the best of a weak group is not an A just for being first, and a project about as weak as the bottom reference is an F whatever its ranking.

Reference projects never appear in the rankings. The Grading curve page shows both of them, their exact prompts, every grading run and every number used. Every report also shows its rank in its category (for example "#3 of 41 in Games"), and your raw score is always shown unchanged.

What a LetsVibe grade is not

  • Not a security audit. A published report never certifies that software is safe to run.
  • Not an endorsement of a project, its author or its fitness for any purpose.
  • Not perfectly repeatable. AI models vary slightly from run to run, so the same code can score a few points differently. Treat small differences between projects as a tie.
  • Not a judgement of a person. Grades describe a repository at one commit, under one rubric version.

Corrections

AI reviews can get facts wrong. A project's owner can report an error in any statement of their review, pointing to the relevant code. The statement is checked once against the code; if the check confirms the error, the statement is corrected (in live data and backups) and the report shows that it was corrected. Otherwise it is reviewed by hand. Scores are not changed by a correction; the owner can request a fresh grade after pushing a new commit.

Why everything runs locally

The models run through Ollama on a single consumer graphics card owned by LetsVibe. Nothing you submit is sent to OpenAI, Anthropic, Google or any other AI provider, and nothing is used to train models. The trade-off is speed: an evaluation takes several minutes and runs one at a time.
